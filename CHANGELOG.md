# История версий KUMOsystems

Записи — от новых к старым. Подробности каждой версии — по ссылкам в тексте.

Версия 1.2 (17.10.2026) — несколько видов съемки, критерий стоимости, диагностика и поиск.

- **Третий критерий** «Минимум стоимости» J = α·T + cᵀt + tᵀQt в условных единицах (у.е.): T — срок
  операции, t_i — налет борта за все вылеты, c — цена часа налета каждого борта, Q — симметричная
  положительно полуопределенная матрица по бортовым номерам. Распределение по приращению J;
  ограничения те же. J считается для любого плана; «Сравнить 3» показывает три плана на одних
  данных и график компромисса «срок — стоимость налета» с диапазоном α для каждого варианта.
- **Коэффициенты J по открытым данным** (после проверки заказчиком: при α = 60, q = 30 и без cᵀt
  J ≈ α·T и повторял план «Быстрее»): α = 2 491 у.е./ч (бригада из двух операторов по медианной
  зарплате с взносами + транспорт), c = λ × цена борта + износ АКБ (Gemini 1 890, 201 2 833,
  801 3 400 у.е./ч; λ = 10⁻³ на летный час по Petritoli et al., 2018), q = λ·(α + c)/2 — риск
  повторного облета (≈ 2–3 у.е./ч²). У каждого числа — статус и источник; 1 у.е. ≈ 1 ₽. «Пример:
  коптеры»: «Быстрее» поднимает оба борта (9,4 мин), «Стоимость» оставляет дорогой 801 на земле
  (14 мин, J 1 023 против 1 214). Модели без c считаются по исходной формуле. c и q можно задать
  по типу борта (`by_profile`): свое значение борта → значение типа → значение по умолчанию.
- **Общий локальный поиск и согласованность критериев**: перенос и обмен галсов, роспуск вылета —
  одинаково для всех трех целей, с несколькими стартами; все цели выбирают из одного набора планов,
  поэтому план критерия не хуже двух других по своему показателю. До этого исправления поиск был
  только у J, и план J оказывался короче плана «Быстрее» (1,01 ч против 1,11 ч на демо). На малых задачах — в пределах 0,3% от полного
  перебора распределений. [Описание](docs/COST_CRITERION.md).
- **Несколько видов съемки**: требования «зоны + вид + параметры качества», стабильные ID зон,
  списки сенсоров у бортов, один сенсор на вылет, смена нагрузки между вылетами (15 мин —
  допущение), проверка совместимости и GSD для каждого требования, покрытие по требованиям без
  суммирования площадей разных видов; карта, зоны, парк, таблица вылетов, отчет и KML показывают
  требование и сенсор. Каталог профилей сенсоров с источниками и пометками параметров,
  демонстрационные LiDAR и магнитометр, пользовательские профили с версиями, импорт и экспорт без
  тихой перезаписи, снимок профилей в сценарии. [Описание](docs/MULTI_SURVEY_AND_SENSORS.md).
- **Диагностика**: категории (ввод, оборудование, ограничения, план не найден эвристикой, бюджет,
  ошибка сервиса), субъекты, фактическое и требуемое значение с единицами, переход к полю и
  объекту на карте; исправление «добавить сенсор борту» — только с предпросмотром и отменой.
  Внутренние ошибки отвечают кодом для журнала. [Описание](docs/DIAGNOSTICS_AND_SEARCH.md).
- **Поиск** по разделам, настройкам и действиям (кнопка «Поиск», Ctrl+K) с синонимами; расчет,
  импорт и экспорт поиск не запускает.
- **Совместимость**: сценарии без новых полей считаются прежним путем; эталонные расчеты из-за
  общего локального поиска изменились сознательно — только в лучшую сторону по своему критерию
  ([VERIFICATION](docs/VERIFICATION.md)); «Преобразовать в требования съемки» не меняет план; старые планы и отчеты
  открываются без пересчета. Для PostgreSQL — «Подготовить схему» (новая таблица
  `sensor_profiles`). Расчет стал в 2–3 раза дольше из-за поиска; анализ парка — без поиска, как раньше.
- Тесты: 254 серверных (было 192) и 52 клиентских (было 41).

Версия 1.1 (25.09.2026) — эшелоны и модель самолета. [Описание](docs/ECHELONS_AND_FIXED_WING.md).

- **Эшелоны**: своя высота борта в карточке парка; автоматические эшелоны от высоты съемки
  вверх с шагом 20 м до потолка 150 м (граница полетов без разрешения на использование
  воздушного пространства), ниже зон и в пределах GSD. Уровни получают борта, чьи маршруты
  проходят ближе 30 м; эшелоны сохраняются, если убирают такие участки ценой не более 5%
  срока. Пример «Эшелоны»: общие участки на одной высоте 8,2 → 0,3 км.
- **Разведение по высоте**: 30 м по горизонтали или 20 м по высоте, точно во времени, в том
  числе на наборе над общей площадкой; минимальная задержка старта вместо ожидания конца
  чужого участка. 20 Gemini на 4 площадках: 33,5 → 23,9 мин, 10 Gemini на одной площадке:
  108,9 → 64,9 мин.
- **Самолет 201**: развороты с постоянным креном, в ветре — трохоиды; шесть видов пути
  Дубинса, включая петли; облет галсов в выгодном порядке (вставка при распределении,
  доработка порядка, облет «через k галсов»); прямой заход на галс 50 м; снос камеры в
  боковом ветре и направления галсов вдоль и поперек ветра; набор по спирали, если прямо не
  хватает места; высота выпуска парашюта со снижением кругами. Пример «201 + Gemini»: налет
  32,4 → 26,4 мин (быстрее завершить), 28,0 → 17,8 мин (меньше налет); переход между
  галсами ≈ 91 → 28 с.
- Предупреждение о высоте выше потолка; высоты в таблице вылетов, отчете и на метке борта.
- Совместимость: сценарии без новых полей считаются как в 1.0; модель 201 изменилась, поэтому
  перерасчет сценариев с 201 дает более короткие планы. Новые сценарии — с эшелонами.

Финальная проверка перед публикацией (27.09.2026):

- Документация по требованиям задания собрана в актуальные документы: [алгоритм](docs/ALGORITHM.md),
  [архитектура](docs/ARCHITECTURE.md) (история решений — отдельно), [API](docs/API.md),
  [ограничения](docs/LIMITATIONS.md), [материалы к презентации](docs/PRESENTATION.md); README —
  главная страница с таблицей соответствия заданию.
- Ключ MapTiler убран из шаблонов `.env.example`; `scripts/package_source.py` собирает пакет
  исходников без локальных файлов и останавливается, если ключ попал в пакет.
- `.gitignore`: правило `coverage/` (отчеты о покрытии тестами) исключало и модуль галсов
  `planning/coverage/` — при публикации через git проект не запустился бы. Правило привязано к
  путям отчетов; упаковщик проверяет, что все пакеты сервиса попали в архив.
- Ответы API объявляют `charset=utf-8`: PowerShell 5.1 больше не искажает русские сообщения.
- Снижение самолета перед выпуском парашюта отмечено как полет на воздушной скорости.
- Масштабная линейка карты читается в светлой теме и не перекрывает атрибуцию; имена бортов в
  таблицах не переносятся посреди слова. Описание примера «Эшелоны» уточнено: общие коридоры.

Версия 1.0 — автономная сборка для Windows (24.09.2026):

- **Запуск без установки**: архив `KUMOsystems-1.0.0-win64.zip` (55 МБ, 161 МБ распакованный)
  с собственным Python, пакетами сервиса и собранным интерфейсом. Двойной щелчок по
  `KUMOsystems.cmd` запускает сервер и открывает браузер; первый свободный порт с 8000,
  повторный запуск открывает уже работающий; данные в `data\` рядом, а если папка только для
  чтения — в `%LOCALAPPDATA%\KUMOsystems\data`. Установленный на машине Python не мешает.
- Сборка `scripts\build-windows.cmd` за ~30 с без загрузок, с проверкой DLL и запуском
  собранного сервера в окружении без Python; ключ MapTiler разработчика в архив не попадает.
  [Описание](docs/WINDOWS_STANDALONE.md).
- `tzdata` добавлен в зависимости: `zoneinfo` на Windows без него не знает часовых поясов.

Версия 1.0 (24.09.2026) — выпуск для сдачи:

- **Темная тема**: переключатель в шапке (☾/☀), выбор запоминается в браузере, без выбора
  тема следует настройке системы. Подложка OSM в темной теме затемняется, подписи на карте
  перестраиваются; печатный отчет остается светлым.
- **Работа без интернета**: подложка «Без подложки · офлайн» — план, маршруты и симуляция
  на сетке, когда тайлы недоступны; сообщения об ошибке тайлов подсказывают этот режим.
- **Проверка проекта**: аудит контраста интерфейса в обеих темах (508 текстовых элементов,
  норма WCAG AA 4,5:1) — исправлены белый текст на ярком оранжевом, имена бортов в цвете
  миссии, второстепенный и статусный текст; устаревшие описания модулей и заглушка очереди;
  повтор борта в предупреждении о резервных площадках при нескольких вылетах; явный тип
  `.svg` для Windows; сборка разделена на части (карта, React, приложение) — без
  предупреждения о размере; значок вкладки.
- Документация: краткий README, [руководство оператора](docs/USER_GUIDE.md), эта история.

Версия 0.9 (24.09.2026):

- **Новый интерфейс в цветах заказчика**: светло-серый и белый, графитовая шапка,
  оранжевый акцент. Три шага «Район → Парк → Параметры» со сворачиваемыми разделами,
  в заголовках которых видны текущие значения; закрепленная панель запуска; результат с
  KPI-карточками, **диаграммой расписания бортов** и таблицей вылетов по часам.
- **Зарядка на площадках**: режим «Зарядка на площадке» вместо замены АКБ. У площадок
  задается число ЗУ (в том числе у запасных), каждое заряжает одну АКБ за раз, борты ждут
  в очереди; коптер может сесть на зарядку на любую площадку с ЗУ и взлететь оттуда.
  Время заряда Gemini — 105 мин по руководству. Нехватка бортов теперь считается, но
  честно занимает много времени: 493 га на 2 Gemini — 12 ч вместо 6,4 ч с заменой АКБ.

[Подробности и ограничения](docs/UI_AND_CHARGING.md).

Версия 0.8 (23.09.2026) — работа с данными заказчика из `additional_docs`:

- **Импорт KML** задания, зон ограничений и препятствий («Территория» → «Данные
  заказчика · KML»). Файлы заказчика читаются целиком: 561 участок задания, 341 зона
  (высоты распознаны из текста у 335), 5162 препятствия.
- **Зоны и препятствия в расчете** — с высотами и временем действия. Зона или
  препятствие облетается, только если достает до высоты полета с запасом; зоны AMSL
  и эшелоны пересчитываются по диапазону рельефа в худшую сторону. Найдено, что
  высоты препятствий заказчика смешанные: часть над землей, часть над уровнем моря
  (видно по `altitudeMode`), и импорт это учитывает.
- **Заблокированные участки** можно исключать из съемки с отчетом о площади
  вместо отказа; «карманы», отрезанные ограничениями от площадок, тоже.
- **Повторные вылеты, срок, лимит бортов, «до заката»** и **анализ парка**:
  сколько бортов нужно к сроку и сколько займет работа с N бортами — прямой ответ на
  вопрос заказчика. **Расход ресурса до ТО** по нормативам 201/801.
- **Задание целиком**: большое задание делится на пакеты работ с оценкой вылетов,
  налета и рабочих дней; выбранный пакет берется в детальный расчет.
- Маршрутизация переписана на A* с ленивой видимостью (сотни препятствий — за
  секунды), расписание не заставляет борта с одной площадки ждать чужой полет
  целиком. Все эталонные расчеты прежних примеров совпадают с 0.7 побитово.

[Подробности, формат зон KUMO и ограничения](docs/AIRSPACE_AND_CUSTOMER_DATA.md).

Версия 0.7 (22.09.2026):

- **Посадка на другую основную площадку.** Новая настройка «Посадка» на вкладке
  «Съемка»: борт может сесть не туда, откуда взлетел, а на ближайшую по времени
  основную площадку; самолет — только если линия сноса парашюта в разрешенном
  пространстве. По умолчанию все как раньше, поэтому сохраненные сценарии
  пересчитываются с прежними результатами. На «Демо 201» при минимальном налете:
  28,0 → 25,5 мин. [Подробности и ограничения](docs/LANDING_SITES.md).
- **Новые иконки БПЛА** от команды, без белого круга и обводки. Линейные рисунки
  перекрашиваются в цвет миссии и получают тонкую темную окантовку, чтобы
  читаться на схеме и на спутнике; те же иконки — в карточках миссий и в панели
  симуляции. [Подробности](docs/AIRCRAFT_ICONS.md).

Версия 0.4 добавляет «Мои карты» (личный MapTiler, XYZ и TileJSON) и «БД компании»
(проверка PostgreSQL, подготовка отдельной схемы, сохранение подключения для перезапуска).
Стандартные карты и их существующий ключ сохранены. Настройки ключей карт остаются
в браузере по выбору пользователя; пароль БД берется из окружения сервера.
[Инструкция по картам и PostgreSQL](docs/MAPS_AND_DATABASE.md).

В версии 0.3 добавлены пользовательские типы БПЛА, погодная панель Open-Meteo
и воспроизведение миссии с движением аппаратов по карте. Подробности и ограничения:
[WEATHER_PROFILES_REALTIME.md](docs/WEATHER_PROFILES_REALTIME.md).

Для симуляции: «Демо-сценарий» → «Рассчитать» → «Воспроизвести». Доступны пауза,
перемотка и ускорение ×1/×10/×30/×60. Это движение по плану, не реальная телеметрия.
Погода: вкладка «Съемка» → «Обновить погоду» → «Применить ветер к сценарию».
Новая модель: «Парк» → «+ Новый тип БПЛА», затем добавить ее экземпляр в парк.
Дополнительные проверки frontend: npm test.
