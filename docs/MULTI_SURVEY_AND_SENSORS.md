# Несколько видов съемки и профили сенсоров

Версия 1.2 (17.10.2026). Код: `backend/src/bas/domain/models.py` (`SurveyRequirement`,
`SensorProfile`), `planning/tasks.py` (требования → задачи, сенсоры бортов), `catalog/sensors.py`
(встроенные профили, геометрия съемки), `catalog/sensor_service.py` (пользовательские профили),
`domain/migration.py` (преобразование 1.1 → 1.2). Интерфейс: «Параметры → Требования съемки»,
«Парк → карточка борта → Сенсоры», «Парк → Профили сенсоров».

## 1. Модель

**Зона** — полигон съемки со стабильным идентификатором (`area_ids`, например `field`, `plant`).
Идентификатор не меняется при удалении или добавлении других зон.

**Требование съемки** — единица работы: *зоны + вид съемки + параметры качества*:

| Поле | Смысл |
|---|---|
| `id`, `name` | идентификатор и название («Поле · ортофото») |
| `area_ids` | зоны требования (одна или несколько) |
| `survey_type` | `rgb`, `multispectral`, `thermal`, `lidar`, `geophysical` |
| `side_overlap_percent`, `front_overlap_percent` | перекрытия |
| `max_gsd_cm` | предел GSD (кадровые камеры) |
| `altitude_m` | фиксированная высота съемки требования; пусто — высота/эшелон борта |
| `swath_width_m` | ширина полосы, если геометрия сенсора не подтверждена (или чтобы задать вручную) |
| `line_spacing_m` | шаг линий для съемки по линиям (магнитометрия) |
| `max_speed_mps` | предел скорости съемки |

Одна зона может входить в несколько требований (поле: ортофото + вегетация). Каждое требование
покрывается и проверяется отдельно; **площади разных видов не суммируются**: в результате —
таблица «Покрытие по требованиям», в отчете — раздел «Требования съемки».

**Сенсоры борта** (`fleet[].sensors`) — список профилей, которые есть у борта. Это заявление
оператора о комплектации: сервис его не проверяет, но проверяет совместимость профиля с моделью.

**Вылет** выполняется одним установленным сенсором. Одновременная съемка разными сенсорами не
планируется. Если следующий вылет борта — с другим сенсором, перед ним добавляется смена
нагрузки `settings.payload_change_min` (по умолчанию 15 мин — консервативное допущение
демонстрации; «Параметры → Вылеты и зарядка»). Смена видна в таблице вылетов («замена АКБ 15 +
смена нагрузки 15 мин») и удлиняет T, но не налет t_i.

**Единица планирования** — борт + сенсор + высота + скорость. Борт может выполнить требование,
если у него есть сенсор того же вида, совместимый с моделью, и геометрия дает допустимую полосу.

## 2. Проверки соответствия

Для каждого требования и каждого борта (`tasks.build_units`):

- сенсор того же вида: RGB-камера не считается ИК или LiDAR;
- профиль сенсора известен (в каталоге или в снимке сценария);
- совместимость с моделью БПЛА: встроенная модель — только профили, где она указана в
  `compatible_profiles`; пользовательская модель — любой профиль (оператор отвечает за
  комплектацию); «нагрузка без профиля» (`generic_<вид>`) — заявление оператора, как ручная ширина в 1.1;
- GSD на высоте требования/борта не хуже предела (иначе — максимальная допустимая высота);
- геометрия: кадровая камера — полоса H·w/f и GSD; сканер — 2·H·tg(FOV/2); съемка по линиям —
  шаг линий из требования; геометрия не подтверждена — нужна `swath_width_m` требования;
- самолет: высота ≥ 100 м и скорость в диапазоне модели; ветер меньше воздушной скорости.

Если требование не может выполнить никто, расчет не начинается: диагностика называет требование,
зоны, борта и причину по каждому (см. [диагностику](DIAGNOSTICS_AND_SEARCH.md)).

## 4. Пользовательские профили

«Парк → Профили сенсоров → + Новый профиль»: название, вид, геометрия (для кадра — матрица в мм,
фокусное в мм, разрешение в пикселях; для сканера — угол обзора), совместимые модели, источник
(обязательно), ссылка, дата проверки, отметка «демонстрационный». Сервер проверяет полноту
геометрии и диапазоны и отвечает понятной ошибкой.

- **Версии.** Изменение пользовательского профиля сохраняется как новая версия (v2, v3…);
  прежние версии остаются (`GET /api/catalog/sensors/{id}/versions`). Встроенный профиль
  изменить нельзя — «Создать копию».
- **Снимок в сценарии.** При сохранении сценарий получает копию профилей своих бортов
  (`sensor_profiles`); план и повторный расчет используют эту копию, поэтому правка профиля не
  меняет сохраненные расчеты. Если в каталоге появилась новая версия, раздел профилей предложит
  «Считать по версиям из каталога» — только по нажатию.
- **Идентификаторы** создаются из названия транслитерацией (`user_teplovizor_…`), при совпадении —
  с номером.

### Формат обмена (версия 1)

```json
{"format": "kumo-sensor-profiles", "format_version": 1, "exported_at": "2026-10-17T…Z",
 "profiles": [{"id": "user_x", "version": 1, "origin": "user", "name": "…", "sensor_type": "thermal",
               "geometry": "scanner", "field_of_view_deg": 50, "compatible_profiles": ["gemini"],
               "source": "…", "source_url": "", "checked_at": "2026-10-01", "demonstration": false,
               "parameters": {"field_of_view_deg": {"status": "confirmed", "source": "…"}}}]}
```

Экспорт: «Экспорт» у профиля или «Экспорт всех» (`GET /api/catalog/sensors/export[?ids=…]`).
Импорт: «Импорт JSON» (`POST /api/catalog/sensors/import?on_conflict=…`):

- файл другого формата или версии — отказ с причиной; ошибки полей — с номером профиля и полем;
- новый ID — добавляется; тот же ID и то же содержание — пропускается;
- **конфликт** (ID встроенного профиля или пользовательского с другим содержанием): по умолчанию
  ничего не импортируется и показывается список; дальше оператор выбирает «как новые версии»
  (только для пользовательских) или «под новыми ID». Тихой перезаписи нет.

## 5. Совместимость со сценариями 1.1

Сценарий без `requirements` считается как раньше: один вид съемки на все зоны, прежним путем
(до появления общего локального поиска 20 из 20 эталонных расчетов `scripts/benchmark.py`
совпадали с 1.1 побитово; поиск для всех критериев сознательно улучшил 9 из них — см.
[VERIFICATION](VERIFICATION.md)). В интерфейсе раздел «Требования
съемки» предлагает «Преобразовать»: одно требование `survey` «Съемка» на все зоны с прежними
перекрытиями и пределом GSD (или ручной шириной), у бортов — список сенсоров из выбранной
камеры или `generic_<вид>`. План после преобразования совпадает (тест для всех примеров
contracts/; интерфейс и сервер преобразуют одинаково — `scripts/test-requirements.mjs`).
Отменить — «Отменить» над картой. Старые планы и отчеты открываются без пересчета.

## 6. Демонстрационный сценарий

«Пример: виды съемки» = `contracts/scenario.multisurvey.example.json`: поле (≈ 78 га) —
ортофото с GSD ≤ 2,5 см и вегетация (Pollux), завод (≈ 42 га) — тепловизор с полосой 60 м;
Gemini-01 с PF1B и Pollux, Gemini-02 с PF1B, 801-01 с тепловизором, Gemini-03 с Pollux; до 3
вылетов. Модель стоимости не задана — J считается по коэффициентам из открытых данных
([COST_CRITERION §3](COST_CRITERION.md): α = 2 491 у.е./ч, c = 1 890 у.е./ч для Gemini и 3 400 для 801).
Результат сравнения (17.10.2026, T и L — мин):

| Цель | T | L | J, у.е. |
|---|---|---|---|
| Быстрее завершить | 66,5 | 122,7 | 7 378 |
| Меньше налет | 105,2 | 120,4 | 8 912 |
| Минимум стоимости | 66,5 | 122,7 | 7 378 |

Почему так. «Меньше налет» не ценит срок: Gemini-01 делает три вылета подряд (RGB, смена
нагрузки, два мультиспектральных), Gemini-03 — один, поэтому срок 105 мин при самом малом налете.
Налет почти не зависит от плана — его основная часть уходит на саму съемку, — а срок отличается на
39 мин. При цене часа бригады 2 491 у.е. J выбирает быстрый план. График компромисса в сравнении
показывает, где J изменил бы выбор: промежуточный вариант (68,7 мин) выгоднее при α от 83 до 607
у.е./ч, план «Меньше налет» — при α ниже 83. 801-01 во всех планах один: тепловизор есть только у
него. Пример, где J расходится с «Быстрее», — «Пример: коптеры»: 801 дороже в час налета, и
поднимать его ради 4,6 мин невыгодно, пока α < 4 960 у.е./ч. Значения не подбирались под результат.
